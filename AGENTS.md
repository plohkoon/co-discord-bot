# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**co-bot** is a modular Discord server-management bot **plus a first-class Rails web app**, sharing one database. It is multi-guild by design — never hardcode guild IDs; every guild-owned table is scoped by `guild_id`. The first (and currently only) module is **team management**: admins create teams, applicants `/apply` via a Discord modal, officers accept/reject with persistent buttons, and the bot auto-assigns team roles. The web app lets members log in with Discord to manage the same teams, questions, applications, and notes.

Rails 8, Ruby 3.4.1, discordrb 3.8, SQLite (WAL), Solid Queue, ViewComponent + Tailwind v4, `acts_as_tenant`.

## Commands

```bash
bin/setup                 # install gems + prepare DB (add --skip-server to not boot)
bin/dev                   # foreman: web (bin/rails server) + tailwind watch + bin/bot + bin/jobs
bin/rails server          # web only
bin/bot                   # Discord gateway only (standalone, boots full Rails env)

bin/rails db:prepare      # create + migrate
bin/rails db:test:prepare # sync test schema

bin/rails test                                  # unit/integration tests
bin/rails test test/models/team_test.rb         # single file
bin/rails test test/models/team_test.rb:42      # single test at a line
bin/rails test:system                           # Capybara system tests

bin/rubocop               # lint (rubocop-rails-omakase house style)
bin/brakeman --no-pager   # Rails security scan (runs in CI)
bin/bundler-audit         # gem CVE scan (runs in CI)
```

CI (`.github/workflows/ci.yml`) runs brakeman, bundler-audit, importmap audit, rubocop, `test`, and `test:system`. All five are **required status checks on `main`** (admins can bypass), so a red PR can't merge.

**Deploy is automatic on merge to `main`** — `.github/workflows/fly-deploy.yml` runs `flyctl deploy --remote-only` to Fly. It's chained to CI via `workflow_run` rather than its own `push` trigger (the two used to race, so a merge with failing tests still shipped); `needs:` can't cross workflow files, which is why it's `workflow_run` and not a job in `ci.yml`. It checks the triggering run's `conclusion == 'success'` **and** `event == 'push'` — this job holds the Fly token, so a green `pull_request` run must never reach it — and checks out `workflow_run.head_sha` so the deployed commit is exactly the one CI validated, not whatever the branch tip has since become. **Migrations need no release step:** `bin/docker-entrypoint` runs `db:prepare` whenever the command is `bin/rails server`, which the Dockerfile `CMD` satisfies. Editing this workflow only takes effect once it's on `main` — `workflow_run` always uses the default branch's copy.

Environment: copy `.env.example` → `.env`. Needs `DISCORD_BOT_TOKEN` (with **Server Members Intent** enabled in the portal) and `DISCORD_CLIENT_ID/SECRET` for web OAuth — from a **dev-only Discord application**; production uses a separate app whose credentials live in Fly secrets (a shared token would deliver gateway events to both environments). Commands register per guild on join. `bin/bot` idles gracefully when the token is missing, so `bin/dev` won't crash-loop before credentials exist.

## Architecture

### One process, three concerns

In development, `bin/dev` runs web, CSS watch, bot, and jobs (`bin/jobs`) as **separate Procfile processes**; jobs go through Solid Queue in dev too (own SQLite queue DB), matching production. In production, set `RUN_DISCORD_BOT=1` and `SOLID_QUEUE_IN_PUMA=1` (both in fly.toml) and `bin/rails server` boots everything in one unit: `config/puma.rb` loads `plugin :discord_bot` (`lib/puma/plugin/discord_bot.rb`), which **forks a supervised child** running the gateway — mirroring how Solid Queue's Puma plugin forks. The child gets its own AR connection pool (it clears inherited connections on fork), and the plugin ties the child's lifecycle to Puma's: if either dies, both come down so the process manager restarts the whole unit.

**The bot and web app never share in-process state** — they communicate only through the shared DB (and Solid Queue jobs). This is deliberate; keep it that way.

### Multi-tenancy (`acts_as_tenant`)

The tenant is `Guild` (its PK **is** the Discord snowflake). Guild-scoped models include the `GuildScoped` concern (`acts_as_tenant(:guild)`), so queries auto-scope and `guild_id` auto-fills on create. The current tenant is set at exactly **two entry points**:

- Web: a `before_action` in `app/controllers/concerns/guild_scoping.rb` wraps requests in `ActsAsTenant.with_tenant(@guild)`.
- Bot: `CoBot::Runner#with_tenant` wraps every dispatch in `ActsAsTenant.with_tenant(guild) { ... }`.

Background jobs/services that run outside a request (e.g. `Memberships::RoleSync`) must set the tenant themselves with `ActsAsTenant.with_tenant(guild) { ... }`.

### The bot layer (`app/bot/`)

- **`CoBot::Runner`** (`app/bot/co_bot/runner.rb`) owns the single `Discordrb::Bot`, installs signal traps, and runs the supervised restart-with-backoff loop (`run_supervised`). discordrb dispatches each gateway event on its own bare thread, so **every handler body must run inside `Rails.application.executor.wrap`** — `Runner.handle` does this; do not skip it or you leak AR connections.
- **Commands = one class per command, namespace = Discord path.** `Commands::Team::Member::Accept` → `/team member accept`; `Commands::Guild::Create` → `/guild create`. Base is `Commands::Base` (`app/bot/commands/base.rb`). Each class colocates: its option DSL (`string`/`role`/`channel`/… with `required:`/`autocomplete:`), permission gate (`admin_only!` / `officer_only!`, **enforced in-handler**), `autocomplete_<option>(query)` resolvers, and a single-ack response API (`respond` / `show_modal` / `update_message` — each interaction may be answered exactly once; `ack!` guards double-answers). The surface is **split by permission tier**: `/team` is member/officer-facing (no `default_member_permissions`, visible to everyone), while `/guild` is server-wide admin and carries a native **Manage Server** `default_member_permissions` (manifest `permissions: :manage_guild` → registry `PERMISSION_BITS`). Discord's `default_member_permissions` is per-**top-level-command**, so a per-team "officer" (a custom role, not a Discord bit) can't be expressed there — officer gates and `/team edit`'s Manage-Server `position` option stay in-handler, and admin gates stay as defense-in-depth (an admin can override the default in Server Settings → Integrations).
- **Components** (persistent buttons/modals) are `Commands::Components::*` classes declaring `component :button/:modal, "key", params: [...]`. Their custom_ids survive bot restarts.
- **Manifest = `config/commands.rb`** via `CoBot::CommandRegistry.draw`. A single nested `command` keyword builds the tree (a `command` with children = subcommand group, without = leaf — no separate group/subcommand keywords, like Rails routes). **Each leaf's class is auto-discovered from its path**; pass `class:` only to override. `CommandRegistry` (`app/bot/co_bot/command_registry.rb`) turns the manifest into Discord registration, a `path → class` dispatch table, and autocomplete lookup. On sync it upserts each top-level command and **prunes any guild command no longer in the manifest**.
- **Discord constraint:** max 2 nesting levels, and options always trail the leaf subcommand. Current surface: `/team list|apply|edit` + `/team member accept|reject|note|remove` (single-team, everyone-visible; edit/member are officer-gated in-handler) and `/guild create|roster` + `/guild category|type add|edit|remove` (Manage Server — server-wide admin; manage the curated roster lists).
- **Message actions = automatic responses to ordinary messages**, mirroring the command layer: one class per action in `app/bot/message_actions/` (base declares `match word:/contains:/pattern:` + `perform`), listed in the **`config/message_actions.rb`** manifest via `CoBot::MessageActionRegistry.draw` with path-discovered classes. The runner's `dispatch_message` skips bot authors and DMs, matches content **before** any DB work, then runs matching actions inside the tenant. Requires the **Message Content privileged intent** (portal toggle on both dev and prod apps) — discordrb 3.8 predates it, so `Runner::MESSAGE_CONTENT_INTENT` passes the raw bit.

**Scheduled events = native Discord events, mirrored into a channel.** Discord's Events tab owns the calendar, the Interested list and the start notification; what it never does is post to a text channel, which is the whole of co-bot's job here — **we never create or edit events, only mirror them**. Off until `guilds.events_channel_id` is set (guild page, Manage Server). discordrb 3.8 has *zero* scheduled-event support, so both halves are raw: `Runner::SCHEDULED_EVENTS_INTENT` (`1 << 16`, **not** privileged — no portal toggle) plus one `bot.raw` handler filtered by `SCHEDULED_EVENT_DISPATCH` for CREATE/UPDATE/DELETE (USER_ADD/USER_REMOVE are deliberately ignored), and `BotApi#guild_scheduled_event(s)` for reads. `GuildEvents::Sync` is the state machine: it upserts a `GuildEvent` (its `status` enum holds **Discord's own integers**, 1–4) and — doing no network I/O, since it runs on the dispatch thread — enqueues `GuildEventAnnounceJob` (new event), `GuildEventStartJob` (→ ACTIVE), and `GuildEventCleanupJob` at `ended_at + Sync::CLEANUP_DELAY` (1h) once terminal; a DELETE cleans up immediately, since the event's card would be a dead link. Every side effect is guarded by a stored message id / timestamp, so re-delivery is a no-op. **Both posts are built around the bare event URL** — Discord unfurls it into a native event card that tracks the event's live state itself (including flipping to "ended"), which is what makes the 1-hour delay worth having and means nothing ever needs repainting. The announcement is the URL and **nothing else**: the card already renders the name, start time, location and an Interested button, so a line above it only repeats itself. The start post is the one exception — its "come join in" nudge is the whole reason it exists. **Role pings come from the event description** (`Discord::RoleMentions`): Discord treats description text as inert, so a lead typing `@Raid Team` there costs nothing — co-bot resolves it against the guild's **live role list** (names contain spaces, so it's a name-list match, longest name first, not a pattern) and pings it on both the announcement and the start post. **Mentionable roles only** — a non-mentionable one is skipped rather than posted as a mention that would render as dead text without Mention All Roles, which keeps the guild's own setting authoritative and means no new permission to check. `@everyone`/`@here` can never resolve, `allowed_mentions.parse` stays empty so only explicitly-listed role ids can fire, and **the description is never echoed into a post** — only ids are taken from it, so unmatched `@whoever` text can't leak either. A role lookup failure degrades to no pings rather than blocking the post. **Setting, changing or clearing the channel moves the posts** (`Guild`'s `after_update_commit` → `GuildEventsResyncJob`, so every surface that edits the setting is covered). It vacates the old channel first — deleting rather than abandoning, since once a row points elsewhere `GuildEventCleanupJob` (which deletes by the event's recorded `channel_id`) would never reach the old posts — then backfills the new one from `BotApi#guild_scheduled_events`, **oldest first by snowflake id, which is creation order** (the event object carries no created_at). REST is the only way to reach events created while the feature was off: `Sync` ignores everything until a channel exists, so a first-time config has no rows at all. Discord's list endpoint drops completed/canceled events (verified live), and `LIVE_STATUSES` filters anyway, so finished events are never resurrected. Posting runs **inline via `perform_now`, in order** — queue workers would race and shuffle the back catalogue — and each post keeps its own job's guard, so a retry after a rate limit resumes instead of double-posting. **Don't trust the gateway alone for start/end:** Discord flips EXTERNAL events to ACTIVE/COMPLETED automatically and those dispatches aren't dependable (a disconnect drops them outright), so `GuildEventReconcileJob` is scheduled at each of the event's own timestamps + `BACKSTOP_GRACE` and re-reads it over REST through the same state machine. Voice/stage events with no end time have no end backstop — they rely on the gateway COMPLETED.

### Domain model

`TeamMembership` is the durable person×team anchor (not the application): status `pending|active|archived`, `has_many :team_applications` (dated events) and `:membership_notes`. `TeamApplication` belongs to a membership with a `source` enum (`applied` via /apply, `manual` when a role is granted directly). State machine: apply → pending; accept or manual role grant → active; reject / role removed / member leaves → archived; re-apply on archived → pending. Role auto-sync uses the **Server Members privileged intent**: a `member_update` listener reconciles each team's role membership; `member_leave` archives. `Memberships::Backfill` sweeps existing role holders into a new team: `/team create` enqueues `TeamBackfillJob` (Solid Queue), which pages members over REST (`BotApi#each_guild_member` — no gateway needed) and reports the count via an interaction-token follow-up (`BotApi#interaction_followup`, valid ~15 min after the ack; best-effort). `Memberships::RoleManager` is the hierarchy-safe grant/revoke shared by buttons and commands (the bot needs Manage Roles **above** the team role).

`ApplicationQuestion` makes application questions configurable per team (Discord modal caps at 5 inputs).

**Team roster/directory:** teams carry free-form roster details (`Team::ROSTER_FIELDS`: emote — decorates the heading before the role mention; accepts unicode, `:name:` (normalized to `<:name:id>` by `Discord::EmoteResolver` against the guild's emoji list, since bots must post the full mention form), or a raw mention — plus the progression, requirements, date_and_time, current_needs lines). **Every free-typed field** (team/category/type names + the roster lines, both surfaces) gets lenient inline resolution at save time (`EmoteResolver.resolve_text`: known `:name:` shortcodes → mentions, unknown ones stay as typed — free text legitimately contains colons); only the standalone emote field is strict (unknown `:name:` rejects the save), a `position` (sort order within category), an optional `TeamCategory` (directory section header), and an optional `TeamType` (the "type" roster line, e.g. "Heroic Team"). **Categories and team types are curated per-guild lists** — teams pick from them (`.named` is a lookup, never a create): manage them via `/team category|type add|edit|remove` (admin) or the guild page's "Roster settings" section (Manage Server); `TeamType::DEFAULT_NAMES` (Normal/Heroic/Mythic/PvP Team) is seeded by `Guild.sync_from_discord` for new guilds. Teams can be renamed (`/team edit name:` — officer-level — or the web team form). Set roster details via `/team create|edit` options, the web team page, or the web **New team** form (`teams#new/create` — role/channel pickers fetched over REST and submitted ids validated against those lists; Manage Server comes free via `GuildScoping`; creation enqueues the same `TeamBackfillJob`). `/team roster` (admin) posts the directory as **Components-V2 messages** (`CoBot::RosterMessage` builds raw payloads — discordrb 3.8 predates V2 — sent over REST via `BotApi`): one seamless message with `## Category` headers and **one container per team whose accent border is the team role's live color**, each holding a section with the team block and its Apply button inline as the accessory (`Components::ApplyButton`, same modal flow as `/team apply` via shared `Commands::ApplyFlow`). Budgets: 40 components / 4000 text chars per message — `payloads` chunks and re-states headers when overflowing. Mentions never ping. Teams record roster_channel_id/message_id at post time (several teams usually share one message); anything that changes what the roster shows — team create (via `TeamBackfillJob`'s tail, after officers are seeded), team edit/rename (bot or web), category or team-type edits/removals (bot or web), officer-role changes — enqueues `RosterRefreshJob`, which **reflows the whole directory**: rebuilds payloads from all active teams, edits existing messages in place, posts extras when it grew, deletes leftovers when it shrank (hand-deleted messages are reposted; a vanished channel clears all stored ids). No-op until `/team roster` is first posted.

**Officers mirror (`team_officers`):** who holds each team's officer role, kept locally so nothing pages the guild member list at render time. Maintained by `RoleSync.sync_officer` on every `member_update` (and cleared on `member_leave`), seeded + pruned by `Memberships::Backfill` at team creation — Backfill's single member-pagination pass is the **only** full member scan in the app. The roster's "Team Leads" line reads this table; live-role checks are still used for authorization (`officer_for?`).

**Pending-application lifecycle:** one pending application per person×team, enforced three deep (the `/team apply` pre-check, `Applications::Submit`'s `DuplicatePending`, and a partial unique index). `Applications::Timeline` schedules exact-timestamp Solid Queue jobs at submit time — officer reminders at 24h/3d/6d and auto-reject at 7 days — and every handler short-circuits if the application was decided (`Decide`'s row-lock claim wins races). `team_applications.reminder_stage` records what's been sent; overdue jobs firing together after worker downtime collapse into one reminder ("only the latest due stage sends"). Auto-reject goes through the same `Decide` path as the buttons — `decided_by_discord_id: nil` means the system decided — and repaints the review message over REST. The same system-decision path resolves applications stranded by role changes: `Memberships::Archive` rejects any still-pending application (role removed / member left / officer removal) so an archived membership never strands a pending row that would block re-applying via the unique index, and `Memberships::Activate` accepts one (a manual role grant while an application is pending IS the acceptance — no synthetic record). Role-sync reconcile (`Archive.for`) never touches *pending* memberships: an applicant lacking the team role is the expected state, so unrelated role changes can't reject a live application. `co_bot:cleanup_stranded_applications` sweeps rows stranded before these rules existed. The queue DB is therefore durable business state, not just plumbing: dropping it drops the timers.

**Guild install-state reconciliation:** `Guild#removed_at` marks servers the bot was kicked from — rows (and team data) are never deleted, so re-inviting restores everything. It's stamped by the `server_delete` handler, by `sync_all_guilds` on every `ready` (two-way: upserts present guilds, marks missing ones), and by `Discord::GuildHealth` on a REST 404; it's cleared by any `Guild.sync_from_discord`. Web treats removed guilds as not installed (`Guild.installed` scope, blocked in `GuildScoping`) and the dashboard shows a re-invite card. `Discord::GuildHealth` (web-side REST via `Discord::BotApi` with the bot token, cached 60s) powers the permission-warning banner on the guild page — it mirrors the invariants `Memberships::RoleManager` enforces at action time.

**Install wizard:** `Discord::ManageableGuilds` partitions the user's Manage-Server guilds at login into `manageable` (Guild row exists — ids in the session) and `installable` (no row — full `{id,name,icon}` stored in `users.installable_guilds`, JSON-serialized, since the cookie is size-capped and there's no Guild row for names). The dashboard renders installable servers as "Add co-bot" cards linking to `discord_install_url` (helper owns `BOT_INVITE_PERMISSIONS`; the URL's `permissions` param overrides any portal defaults). A Stimulus `install-poll` controller polls `GET /install_status` and reloads when the bot's `server_create` lands the Guild row; `ApplicationController#manageable_guild_ids` auto-promotes installable ids whose row now exists (Manage Server was verified at login), so no re-login is needed after an install.

Business logic lives in `app/services/` (e.g. `Applications::Submit`, `Applications::Decide`, `Memberships::Activate/Archive/RoleSync/RoleManager`), not in commands or controllers.

### World of Warcraft (Battle.net) integration

**Battle.net links are per-person, not per-guild** — `battle_net_accounts` hangs off `User`, so a user links once and it applies in every server. Deliberately *not* `GuildScoped`.

**A character belongs to a USER, not to a Battle.net account.** `wow_characters.user_id` is the relationship; the Battle.net account is *evidence*. Requiring the OAuth link made anyone unwilling to authorise invisible to the whole pipeline, which is the wrong constraint for an application flow — an applicant should be able to say "this is my character" and have a reviewer see their gear and parses regardless.

- **`verified_at` and `claimed_at` are separate columns, not one status.** Verified = Blizzard confirmed ownership via OAuth. Claimed = the user asserted it, unproven. A claim that is later verified is *both*, and that distinction is exactly what a reviewer needs — `#ownership` returns `:verified`/`:claimed`, and anything showing a character to a third party must render it rather than presenting an assertion as fact.
- **One row per real character**: `blizzard_id` is globally unique (verified — no duplicates across accounts), so a claim and a later OAuth verification **converge on the same row** instead of forking, and the refresh jobs never do the same character twice for two people pointing at it.
- **A claim can never take a character from someone.** `WowCharacters::Claim` refuses if the character is already verified *or* claimed by another user — it is the weakest signal in the system and must not also be the most destructive. Conversely OAuth verification *does* take the row over, since Blizzard outranks any assertion.
- `LinkAccount#prune` **demotes** a claimed character back to a claim when it leaves a Battle.net account rather than deleting it: losing the proof shouldn't also lose the assertion, or someone's data would vanish from an application they'd already submitted.
- **Main character** (`users.main_wow_character_id`) — a pointer, not a flag on the character, so "exactly one" is structural rather than something a callback must keep true. `WowCharacters::SetMain` distinguishes `ensure` (fills a gap: first claim, or inferred after a link by level then last-login) from `set` (an explicit choice that inference never overrides). It also self-heals a dangling pointer when a main is released or goes missing. All three FKs to `wow_characters` are `ON DELETE SET NULL` — without it, releasing your own main fails on a constraint.
- **`team_memberships.wow_character_id`** is the character someone plays *on that team*, distinct from their main because it genuinely differs (main a tank, raid as a healer). Seeded from the application, changed by leads — scoped to characters the member owns, so a lead can correct a swap but not attribute a stranger's character.
- **Applications capture a character** (`character_input` verbatim + `wow_character_id` resolved). Resolution runs out of band in `ApplicationCharacterJob` because it costs a Blizzard round trip and **an application must never be lost or delayed by a typo**. The two columns encode three states: no input (team doesn't ask), input without id (unrecognised — the applicant gets a DM, officers still see what was typed), both (resolved and claimed). The character input takes one of Discord's five modal slots, so `Team#question_limit` drops to four when `collect_character` is on; the migration opts out teams already using all five.
- **`Applications::RaiderSummary` is about four states, not formatting.** `:not_asked` / `:loading` / `:failed` / `:ready` — and three of them render as "no data" if you're careless. An officer reading "no parses" about someone who has a 99 is worse than showing nothing, so each state says what it is. **Order matters in the check**: "haven't looked yet" must beat "found nothing", or every application reads as a typo for its first few seconds. That's what `character_resolved_at` exists for — `character_input` present with no id meant both "still looking" and "no such character" until it was added.
- The review message posts as `⏳ Loading raider data…` and `ApplicationCharacterJob` repaints it via `RefreshReviewMessage` once the answer is known, either way. The job gathers **inline** (`perform_now`) rather than enqueuing, so the repaint has data to show instead of promising a second edit nothing guarantees.
- "Show more detail" is a **link** button, so Discord opens it directly and the full report costs the bot nothing. Omitted when `APP_URL` is unset — a bot job has no request to infer a host from, and a broken link is worse than none.
- `region` is a column on the character, not delegated from the account — it's a property of the realm, and a claimed character has no account to delegate to. A character created *through* an account inherits `user` and `region` via `before_validation`, so callers never restate what the account already implies.

**The token constraint drives the whole design.** Blizzard user access tokens live 24 hours and third parties get no usable refresh token, so **nothing persists a user token**. OAuth is a one-time *ownership ceremony*: `BattleNet::LinkAccount` spends the token immediately to read `/profile/user/wow` — the only endpoint that proves which characters someone owns — writes `wow_characters` with `verified_at`, and drops the token. Everything afterwards runs on the app-level client-credentials token (`BattleNet::Client.app`, cached in `Rails.cache`) against public endpoints, which never expires. Only *discovering newly-created characters* needs a re-link; refreshing a known character does not.

- **`BattleNet::Client`** (`app/services/battle_net/client.rb`) — the reusable REST client, same shape as `Discord::BotApi`. Two modes: `.app(region:)` (client credentials) and `.for_user(token, region:)`. Region picks both the API host (`{region}.api.blizzard.com`) and the namespace (`profile-{region}`); an unknown region falls back to `us` rather than building a bad host. `#get` is public so new endpoints don't need a fork. `cn` is a separate Blizzard deployment and is unsupported.
- **`OmniAuth::Strategies::BattleNet`** (`lib/omniauth/strategies/battle_net.rb`) — hand-rolled, ~40 lines. Blizzard's own `omniauth-bnet` gem is abandoned (2018, pins `omniauth ~> 1.0`, points at the retired `us.battle.net/oauth/*` hosts). Endpoints come from Battle.net's OIDC discovery doc; scope is `wow.profile` and nothing more (`/userinfo` answers on a plain access token — `openid` buys nothing, and no maintained client requests it). `callback_url` is overridden to drop the query string, which Blizzard's exact redirect_uri match rejects.
- **`BattleNet::LinkAccount`** — probes regions in order (preferred first, so the common single-region case costs one request), keys characters on Blizzard's `blizzard_id` (survives renames and transfers, which name+realm does not), and prunes characters that vanish from Blizzard's list. All HTTP finishes before the transaction opens. Returns a `Result` with `ok?`.
- **`Discord::Connections`** — reads `/users/@me/connections` at sign-in (the Discord OAuth scope is now `identify guilds connections`). Discord natively supports `battlenet` as a connection type, so this hands us a user's BattleTag for free. It is a **hint, never proof**: it identifies the account but says nothing about characters. Where both exist they're cross-checked (`BattleNetAccount#matches_discord_connection?`) and a mismatch is surfaced rather than silently resolved. The service is generic over all ~34 connection types, so adding Steam/Xbox later is a lookup.
- Web surface is `/account` (`AccountController`, `BattleNetAccountsController`) — per-person settings, outside `GuildScoping`. Credentials are `BLIZZARD_CLIENT_ID/SECRET`; without them the Battle.net section stays hidden and everything else works.
- **`http://localhost:3000/auth/battle_net/callback` works — https is NOT required.** Confirmed end to end against a live client. Several Blizzard forum threads and an open `passport-bnet` issue claim https is mandatory; they are wrong (or long stale). Don't set up a tunnel or local TLS for this.
- **Blizzard's OAuth errors are misleading; this is what they actually mean**, measured against a live client. `GET /authorize` validates almost nothing: an unregistered `redirect_uri`, an `openid` scope, even `response_type=token` all return 302 to the login page. The only up-front rejection is a missing/malformed redirect_uri (`400 The redirect_uri parameter must be a valid URI`), and an unknown `client_id` is `401 Bad client credentials`. **`400 Invalid grant type or callback URL is not valid` is raised only *after* the user logs in**, when Blizzard finally compares `redirect_uri` against the client's registered list. So it always means a real registration mismatch — and it can't be reproduced without completing a login, which is why probing the authorize URL never reveals it. `bin/rails co_bot:battle_net_oauth_check` prints the exact string to register and independently verifies the id/secret via client credentials.
- `APP_URL` pins the callback origin when the app is reached behind a tunnel or TLS proxy — `OmniAuth.config.full_host` builds callbacks from it and development's `config.hosts` allows the host through. Unset for plain localhost. The client-credentials half needs no redirect URI at all.
- Blizzard's rate limit is 36,000 req/hour and 100 req/sec per client — vastly above current needs, but batch character refreshes through Solid Queue rather than in requests.

**Character refresh (the half that runs forever):** `BattleNet::RefreshCharacter` pulls one character's live data — ilvl, active spec, guild, last login, current-season M+ rating — from Blizzard's **public** endpoints using `BattleNet::Client.app`. No user token is involved, so this keeps working indefinitely after the 24h link ceremony expires; region/realm-slug/name were captured at link time. Two requests per character; the mythic-keystone one 404s for anyone who hasn't run a key this season, which is ordinary and yields `nil`, not an error.

- `WowCharacterRefreshJob` does one character per job (a bad character can't stall an account; a retry re-fetches only what failed). It catches `Client::Unauthorized` to call `Client.expire_app_token` **before** re-raising — `retry_on`'s block runs only after retries are *exhausted*, which would be too late to help.
- `WowCharacterSweepJob` (hourly, `config/recurring.yml`) enqueues stale characters, never-refreshed first. `MIN_LEVEL` and `BATCH` are cost controls — a linked account brings ~50 characters, mostly bank alts — not correctness: oldest-first ordering means nothing is starved, it only waits a pass. Refreshes are also enqueued right after a link and by the "Refresh" button on `/account`.
- **The public endpoint is addressed by name**, so a rename or realm transfer reads as a 404. That stamps `missing_at` (keeping the last known data and excluding the row from future sweeps) rather than deleting anything; a successful read clears it, and re-linking is what actually repairs it. `blizzard_id` is stable across renames but there's no reverse lookup by id.
- Watch out when eyeballing real data: guild names like *"Currently Online"* are real WoW joke guilds, not a parsing bug, and current-expansion item levels are far lower than pre-squish numbers.

**Raider.io (`app/services/raider_io/`)** layers on what Blizzard won't give plainly: **raid progression per tier** and the **M+ score split by role** (`tank`/`healer`/`dps` — Blizzard exposes the spec, never its role, and role is what a lead sorts by when filling a team). Public endpoints, no auth; `RAIDER_IO_API_KEY` only raises the rate limit, so an unset key makes this slower, never broken.

- **Strictly supplementary, by design.** `WowCharacterRefreshJob` runs Blizzard first and commits it, then calls `RaiderIo::RefreshCharacter` in a rescue that swallows `RaiderIo::Client::Error`. Raider.io's limit is 200/min against Blizzard's 36,000/hour, so it is the binding constraint on any bulk refresh — letting it fail the job would re-spend Blizzard requests to fix a Raider.io problem. A miss just waits for the next sweep. A character Blizzard has marked `missing` is never looked up on Raider.io.
- **Raider.io answers an unknown character with HTTP 400, not 404** (`{"statusCode":400,…,"message":"Could not find requested character"}`). `Client` inspects the message to tell that apart from a genuinely malformed request; reading 400 as "our bug" would misclassify every alt Raider.io has never crawled. 429 is its own `RateLimited` error.
- **`mythic_plus_scores_by_season` is an ARRAY**, not a hash keyed by season — asking for `:current` still returns a one-element array. Its `scores` hash carries `spec_0…spec_3` alongside the real roles; only `all/tank/healer/dps` are kept.

**Satellite tables, and the immutability rule behind them.** Raider.io history lives in `wow_character_seasons` and `wow_character_raids`, not in columns on the character, because **a finished season's score never changes**. Each row is fetched exactly once and then only read; only the live season is ever re-fetched. Season selectors colon-chain (`mythic_plus_scores_by_season:current:season-tww-3:season-tww-2`), so a character's *entire* Mythic+ history costs **one** request — measured: 8 seasons on the first pass, 1 per pass forever after. Score history is also the better recruiting signal: "2900+ for three straight seasons" says far more than one current number, and per-season role splits show when someone switched from DPS to tank.

- `wow_seasons` / `wow_raids` are shared reference data (a few dozen rows total), synced weekly by `RaiderIoStaticDataJob` → `RaiderIo::SyncStaticData`. **This has to run before the character refresh can be cheap**: a season's `ends_at` is what proves its scores are frozen. Expansion ids are probed upward (there's no "list expansions" endpoint) until Raider.io answers `Client::Unsupported` — another 400 variant, which is why it's its own error class rather than a message match at the call site.
- `WowSeason::RANKED_SLUG` (`season-<expansion>-<number>`, no suffix) is what excludes Raider.io's event and re-cut slugs — `-break-the-meta`, `-post`, `-post-1017`, `-cutoffs`, `-meta-vs-meta`, `-legion-remix`. Live data: 9 ranked out of 29 total. Only ranked seasons are backfilled.
- Satellites join to reference tables **by slug, not FK** (`belongs_to … foreign_key: :season_slug, primary_key: :slug, optional: true`). Raider.io can report a season the static sync hasn't seen; an unlabelled score beats a dropped one.
- `wow_characters.raider_io_score`/`raider_io_role` remain as a denormalised copy of the **live** season, so listing a team by score stays a single-table query. The live season is identified *by elimination* (whatever isn't in the requested backfill set, all of which are ended) — Raider.io doesn't promise `current` comes back first.

**Warcraft Logs (`app/services/warcraft_logs/`)** adds the third and last leg: **parse percentiles** — how well someone actually played. Blizzard says what gear they have, Raider.io says what they killed, Warcraft Logs says how well. That's what raid leads recruit on.

- **GraphQL, not REST** — one POST endpoint, static query documents as constants, no gem. Auth is OAuth2 **client credentials** (no user consent), token cached like Blizzard's. **Metered by points, not requests**: 3,600/hour, and a query's cost scales with what it asks for — so this is the tightest budget of the three and sits last in the refresh chain.
- **GraphQL reports failures inside HTTP 200.** `Client#unwrap` inspects the `errors` array and re-classifies by message (rate limit / auth / everything else); a 200 status proves nothing on its own. `characterData.character` comes back **null** for anyone never in a logged raid — a successful query with an empty answer, mapped to `NotFound`.
- `zoneRankings` is a **JSON scalar**: it takes arguments but has no sub-selection and returns an opaque object parsed by hand. It answers for exactly **one difficulty** per query, and left unspecified Warcraft Logs picks the hardest the character cleared — which is what a recruiter wants, at half the points of asking per difficulty. A later mythic clear adds a row rather than overwriting the heroic one.
- **`WarcraftLogsZone.closed` is Warcraft Logs' `frozen`**, renamed on the way in because Active Record refuses a `frozen` attribute (it would shadow `Object#frozen?`). It plays exactly the role `WowSeason#ended?` does for Raider.io: a closed tier's parses are final, so its rankings are fetched once and never again. Backfill is **one zone per refresh** (the zoneID is a single argument — no chaining, unlike Raider.io seasons).
- Zones are **deliberately not reconciled with `wow_raids`** (Raider.io's view of the same tiers). The two services slug and split tiers differently; a guessed mapping would quietly corrupt both.
- Entirely optional: `WARCRAFTLOGS_CLIENT_ID/SECRET` unset means `WowCharacterRefreshJob` skips the step and the rest of the pipeline is unaffected. A `Client::Unauthorized` evicts the cached token and logs rather than failing the refresh.
- **Verified against the live API.** Every field name held (`difficulty`, `bestPerformanceAverage`, `medianPerformanceAverage`, `allStars`, `rankings[].totalKills`). Two corrections came out of real data: `bestSpec` is **nil** at the top level, so the spec falls back to `allStars.first["spec"]`; and `allStars` is one entry per **partition** (a tier's sub-periods), not per spec — a live character had three entries all of the same spec, ordered best-first. `bin/rails co_bot:warcraft_logs_check` re-runs the whole verification.
- **Warcraft Logs lists Mythic+ seasons in the same `zones` collection as raid tiers**, and M+ uses **difficulty 10** against mythic raid's 5 — so an M+ row wins any highest-difficulty comparison and hijacks the headline parse (observed live: a raid parse of 99 losing to an M+ 100). `WarcraftLogsZone#kind` splits them off the zone's own difficulty list, and `RefreshCharacter` fetches **raid zones only**. Raider.io score is the M+ metric anyway.
- `WowCharacter#best_ranking` tie-breaks on **kill count** after difficulty and parse. Measured: a 99 Mythic off 5 kills in a one-boss raid was beating a 99 Mythic off 143 kills in the main tier on nothing but a higher zone id.

**Joining Raider.io tiers to Warcraft Logs zones (`wow_encounters`).** The two services carve raid tiers up differently — Raider.io's "MN Tier 1 (VS / DR / MQD)" is one nine-boss tier spanning three instances — so matching them at the tier level is guesswork. Individual bosses are not.

- The intended key was Blizzard's **journal encounter id**, which both services publish. Raider.io fills it in; **Warcraft Logs does not** — verified live, `journalID` is `0` for every encounter in every zone, current tiers and years-old ones alike. The field exists in their schema and is simply never populated.
- So the join **prefers the journal id and falls back to a normalised boss name** (`WowEncounter.normalize` — punctuation and case only, deliberately conservative). Names matched **8 of 9** in the live tier unmodified; the miss was `"Chimaerus, the Undreamt God"` vs `"Chimaerus the Undreamt God"`, and normalising takes it to 9/9. If Warcraft Logs ever starts populating journalID, the preferred path starts working for free.
- The Warcraft Logs sync only **annotates** encounters Raider.io already recorded (`WowEncounter.link_warcraft_logs!`) rather than creating its own — with journalID dead there is no id to key a new row on, and a boss Raider.io never mentioned has nothing to join to. Live: **59 of 103** encounters linked, `tier-mn-1 → "VS / DR / MQD"`.
- `WowRaid#warcraft_logs_zones` and `WarcraftLogsZone#wow_raids` derive the tier mapping from shared bosses rather than asserting it, handling the many-to-many case. There is **no** equivalent key for Raider.io *M+ seasons* — no boss list to join on.

**wowaudit is not a richer source than Blizzard — it is the same source, processed.** Established by reading their open-source engine (`github.com/wowaudit/core`): `Wowaudit::Client` has five retrievers (blizzard, keystones, historical_keystones, wcl, raiderio) and authenticates with a Blizzard client-credentials pair via `RBattlenet`. No addon upload path, no privileged endpoint, no user token. Notably they **derive Great Vault from public data** — `/achievements/statistics` stamps every boss with `quantity` and `last_updated_timestamp`, so anything updated after the weekly reset was killed this week — rather than reading a vault endpoint, because none exists. The practical consequence: **do not build a wowaudit-primary / Blizzard-fallback chain for character stats.** Compute them from Blizzard directly (see `TODOS.md`). wowaudit's genuinely unique data is its **roster and raid signups/attendance** — its own scheduling data, not WoW data — and the integration should stay scoped to that.

**wowaudit (`app/services/wow_audit/`)** answers a different question from the other three: not gear, kills or performance, but **preparation** — enchants, gems, great vault, weekly activity. It is keyed **per raid team** (wowaudit's own unit is a team, key issued by a team admin), so the credential lives on `teams.wowaudit_api_key`, not in ENV, and is gated on Manage Server rather than lead. It's in `Admin::ResourcesController::HIDDEN_COLUMNS`.

- **Auth is `Authorization: <raw key>`** — no `Bearer` prefix — plus `Accept: application/json`. wowaudit publishes no machine-readable spec and its docs render client-side, so this (and the response shapes) came from **its own open-source engine, `github.com/wowaudit/core`, plus two independent third-party clients that call the live API**. Confirmed endpoints: `GET /v1/team`, `/v1/characters`, `/v1/period`, `/v1/raids[?include_past=true]`, `/v1/raids/:id`, and `POST /v1/wishlists`.
- `GET /v1/characters` returns a **top-level array** (not an object with a `characters` key) of `{id, name, realm, class, role}`.
- **`WowauditCharacter` matches to `WowCharacter` by name + realm**, the only key the two sides share — wowaudit issues its own character ids and doesn't publish Blizzard's. Both sides are normalised (downcase, NFC, realm spaces → hyphens) or the match silently never fires. An **unmatched row is the ordinary case**, not a failure: most rosters include people who've never linked Battle.net. `SyncRoster` records what wowaudit says and never touches Discord roles or memberships.
- Keys are verified on save, because wowaudit offers no way to tell a good key from a bad one except by using it — and its 401 is **byte-identical for a wrong key, a malformed key, and no key at all**, so a failure never says *why*. `bin/rails co_bot:wowaudit_probe KEY=…` dumps response shapes (keys and types, never values) for wiring up further endpoints.

**Professions (`wow_character_professions` + `_tiers`, `BattleNet::RefreshCharacterProfessions`)** — one cheap request, but **self-throttling to weekly inside the service** (`professions_refreshed_at`), so calling it from the hourly character refresh costs one request per character per *week*. Skill is tracked per expansion tier, which is why tiers are rows: being capped in Classic Tailoring says nothing about whether someone can craft anything current.

- **Tier ids are NOT chronological.** Measured live: the legacy tiers were assigned in one *descending* batch (2501 Draenor is higher than 2506 Classic), while each new expansion since took a fresh higher id (2875 Khaz Algar, 2910 Midnight). `#latest_tier` uses max id, which is right for anyone who has touched a modern expansion and only misorders characters whose tiers are all legacy — for whom "current tier" is meaningless anyway. Don't tighten this into a chronology claim.
- **Recipes are deliberately not stored.** They ride along in the same response, but one live character had **908** — a far larger dataset than the professions themselves, answering a question nobody has asked yet. `known_recipe_count` is kept so the decision can be revisited with numbers, and adding them later costs no extra request.
- Professions are droppable, so the sync prunes: someone who abandons Enchanting for Alchemy stops showing as an enchanter — and that takes their recipes with it, which is why the known-recipe set is reconciled in full rather than added to.

**Recipes (`wow_recipes` catalog + `wow_character_recipes` join).** Split rather than one fat table because a character knows ~500-900 recipes; duplicating the name and profession per character would make it by far the heaviest table in the schema. The join is two integers, indexed both ways, because both directions are real questions ("who knows this" / "what can this character make").

- **The catalog comes from static game data, not from what characters know.** `/data/wow/profession/index` → `/data/wow/profession/{id}` → `/data/wow/profession/{id}/skill-tier/{tierId}` → categories → recipes. That's the difference between *"nobody knows this recipe"* and *"that isn't a recipe"* — only the first answers whether it's worth finding a crafter. It also carries Blizzard's **categories** ("Void Potions", "Transmutations"), which the per-character payload lacks entirely. Live: **10,964 recipes**, ~46s for a full first sync.
- Recipes belong to a **skill tier**, not a profession — the same profession has a different list every expansion. A closed tier's list never changes, so `SyncRecipeCatalog` skips tiers it already holds and only re-reads each profession's newest (a patch can add to the live one). Steady state ~50 requests instead of ~350.
- The join uses Blizzard's `recipe_id` rather than an FK, like the other satellites: a character can know a recipe the catalog hasn't reached yet, and an unlabelled row beats a dropped one.
- **`WowCharacterRecipe.coverage` exists and should travel with any answer.** Recipe data can only ever cover characters of people who linked Battle.net, so "nobody knows it" and "the person who knows it never linked" are indistinguishable from here. Showing a result without the coverage figure is quietly misleading.
- `/data/wow/recipe/{id}` returns `reagents` but `crafted_item` is often **nil** (verified on Sunsmoke Censer), so the catalog can't be filtered down to "produces an item". Categories are the usable grouping.

**Career achievements (`wow_character_achievements`, `BattleNet::RefreshCharacterAchievements`)** — the one thing no other source supplies. Raider.io reports what someone has killed *now*; only the achievement proves they killed it **while it was current**, which is the entire meaning of Ahead of the Curve and Cutting Edge. It's also the sole retroactive PvP record, since Blizzard serves no historical ratings.

- **Matched by name pattern, not id list**, because Blizzard mints new AOTC/Gladiator achievements every tier and an id list would silently stop recognising the newest — the one people ask about. The four evergreen PvP titles are the exception, pinned by id: matching `/Duelist/` by name also catches **"Darkmoon Duelist"**, a real unrelated achievement.
- **The colon exclusion in the keystone matcher is load-bearing.** Blizzard mints a per-dungeon "Keystone Hero: <dungeon>" alongside the seasonal titles; one live character had **39 of those against 3 real titles**. Live filtering keeps **15 rows of 4,197 scanned**.
- Own slow cadence (`WowCharacterAchievementsSweepJob`, weekly, 30-day staleness, batch 100) because the request is heavy and the data is near-static once earned. Unearned achievements come back in the same list with no `completed_timestamp` and are skipped — a goal is not a credential.

**Mythic+ cutoffs (`wow_mythic_plus_cutoffs`, `RaiderIo::SyncCutoffs`, daily).** The M+ counterpart to `wow_pvp_cutoffs`, but sourced differently: **Blizzard publishes no M+ cutoffs at all** (there is no analogue to `pvp-reward`; `/data/wow/mythic-keystone-season/index` 404s), so Raider.io's computed quantiles are the only source. Two things the PvP cutoffs lack and which earn their columns: a **population denominator** (top 0.1% = 1,136 of 1,135,352 US players — a real percentile, not a bare threshold) and a **faction split** that is not cosmetic (US Horde 4023 vs Alliance 4206 for the same title). Regions are independent ladders (US 4157 / EU 4184 / KR 4206 / TW 4232, measured). A changed bar is a new row, as with PvP. Gotchas: the `season` param is documented optional but omitting it **500s**, and `allTimed*` entries nest their factions one level deeper under a `cutoffs` key — they're skipped, not parsed. `WowSeason.live` (started AND unended) picks the season, because Raider.io announces the next season's slug with a future start date and `unended` alone matches two.

**PvP (`BattleNet::SyncPvpReference`, `BattleNet::RefreshCharacterPvp`)** — PvP inverts the PvE data situation and breaks two assumptions the PvE schema rests on.

- **Blizzard is the only source.** Raider.io has *literally zero* PvP coverage (0 mentions of pvp/arena/rbg/shuffle/honor/conquest across its whole OpenAPI spec — measured), Warcraft Logs is raid-shaped, and Check-PvP / Drustvar / PvPLeaderboard / ArenaTracker expose no usable public API. So there is no enrichment layer to add: `wow_character_pvp_ratings` rides the same app token as the gear refresh and needs no new credentials.
- **A character has many ratings, not one.** 2v2/3v3/rbg carry one each, but Solo Shuffle and Blitz are rated **per specialisation** — one measured character held `shuffle-mage-frost`, `shuffle-mage-fire` and `blitz-mage-frost` at once. `bracket` stores Blizzard's raw slug with `bracket_type`/`spec_slug` parsed out (`WowCharacterPvpRating.parse_bracket`). **`pvp-summary` lists exactly which brackets a character has played**, so the fan-out is read from Blizzard rather than guessed: one request to find out, then one per bracket, and a character with no rated play costs a single request and stores nothing.
- **There is no history to backfill — this is the important one.** Blizzard answers the character bracket endpoint for the **current season only**; there is no historical per-character PvP endpoint at any price. That inverts the Raider.io rule: the live season isn't merely the cheap thing to refresh, it's the *only* obtainable thing, and **a rating not captured while live is gone permanently**. Hence PvP is logged at `warn` in `WowCharacterRefreshJob`, not `info` like the genuinely-deferrable enrichments.
- **`wow_pvp_cutoffs` is why ratings are worth storing at all.** A rating means nothing without its contemporaneous title cutoff, and cutoffs are per bracket *and per spec*: measured live in season 41, the same Shuffle title needed **2205 on one spec and 3171 on another** — a 966-point spread. Cutoffs also drift all season, so a **changed value is a new row** (the unique index includes the value), giving a step history of how the bar moved. `WowPvpCutoff.newest_first` orders by `captured_at, id` — the id tiebreak matters, since same-instant captures otherwise resolve at random.
- `wow_pvp_tiers` turns a bare `tier: {id: 14}` into "Elite (2275+)"; thresholds shift between seasons, hence synced not hardcoded. Note the namespaces differ: seasons and rewards are `dynamic`, tiers are `static`.
- **Not available:** Conquest/Honor *currency* balances — `/currencies` and `/pvp-currencies` both 404. Honor *level* and lifetime honorable kills are on `pvp-summary` and are stored on the character.

**WoW Token (`WowTokenPrice`, `WowTokenPriceJob`)** — `/data/wow/token/index` on the **`dynamic`** namespace (not `profile`), app token, hourly per region. Price is in **copper**; stored raw, `#gold` divides. Rows are keyed on Blizzard's own `last_updated_timestamp`, not fetch time, so polling more often than the token moves is a no-op instead of a stream of fake data points. Blizzard serves no history, so this table *is* the history — which is the point, since the movement is the interesting part.
- **Zero is "no keys this season", not a score.** Raider.io reports `0` rather than omitting the field, and `0` is truthy in Ruby — so `WowCharacter#mythic_score` treats a non-positive rating as absent. Without that, every alt renders a "0 M+" badge and an empty Raider.io season masks a real Blizzard rating. Role scores deliberately keep their zeroes.
- Raid summaries come back empty (`""`) for untouched raids and are dropped. `#raid_progress` sorts by difficulty first (`1/9 M` outranks `9/9 H`), so the headline tier leads.

### Web UI (ViewComponent design system)

**Web access tiers** (per guild, enforced by `GuildScoping`): *viewing* a server needs only membership — `Discord::ManageableGuilds` captures every known guild the user belongs to at login (`session[:member_guild_ids]`), and the `team_officers` mirror grants view access to team leads even when their session predates the role. *Opening a team page* needs Manage Server or a lead (officer) of that team (`require_team_access`; leads get the full officer toolkit mirroring Discord — memberships, notes, accept/reject via `ApplicationDecisionsController` → `Applications::Decide`, member removal via `memberships#remove` → `Memberships::RestRoleManager` + `Archive`, editing the team's details via `teams#update` (mirroring the officer-level `/team edit`), and managing the team's application questions via `TeamQuestionsController`). **Position is the exception**: directory placement relative to other teams is Manage Server only on both surfaces — the bot handler rejects it for non-admins, the web strips the param and hides the field. *Guild-level settings* — team create, health recheck, the curated category/type lists — need Manage Server (`require_guild_manager`), matching the bot's admin-only commands. Views branch on the `can_manage?` / `officer_of?(team)` helpers.

Components in `app/components/`: base `ApplicationComponent`, a `Ui::` kit (`Card/Button/Badge/Avatar/StatTile/EmptyState/Section/PageHeader`), and top-level `StatusBadgeComponent`. Views compose these; form fields use the `.field` CSS class, and `Ui::ButtonComponent.classes(variant:, size:)` styles bare `button_to`/submits. Theme is shadcn-style CSS-variable tokens on a warm charcoal base with a **gold `#FFD166`** accent, in `app/assets/tailwind/application.css` (Tailwind v4, `@source` scans components + views). **Dark-only.** Login is Discord OAuth2 via `omniauth-discord`.

**Admin panel (`/admin`):** app-wide, cross-tenant, gated by the hardcoded `User::ADMIN_DISCORD_IDS` allowlist (`Admin::BaseController#require_admin`; admin cannot be granted through the app). Two generic catch-all routes (`/admin/:model`, `/admin/:model/:id`) drive a reflection-based read-only browser over every `ApplicationRecord` model (`Admin::ResourcesController` — queries run `ActsAsTenant.without_tenant`; add future secret columns to its `HIDDEN_COLUMNS`). `/admin/jobs` is the Solid Queue dashboard (`Admin::JobsController`): tabs for all/failed/scheduled/recurring/processes, retry/discard (single + bulk) on failed executions. Test env has its own queue DB so these pages are testable; `test_helper`'s `sign_in_as(user)` logs in through the OmniAuth callback with the Discord guild fetch stubbed.

## Conventions & gotchas

- **Never do Discord/network I/O inside a DB transaction.** Keep write transactions short.
- **SQLite is intentional.** Keep the schema portable (integer PKs, `t.text` for free-form) so a later Postgres switch stays a config change. Litestream handles off-host backups.
- Guild snowflakes and other Discord IDs exceed 32-bit; store them as `bigint`/`t.text`, never assume they fit an `int`.
- discordrb: start with `bot.run(true)` (positional async flag, **not** `async:`), stop with `bot.stop`.
- **Rate limiting is layered by axis — put a new limit in the layer whose key it needs.** IP-keyed and path-keyed throttles live in `config/initializers/rack_attack.rb` (Rack layer, runs before Rails — cheap, covers anonymous traffic and account rotation; app-wide blanket + stricter per-path rules, all keyed on `req.ip`). Limits that key on an app concept IP can't express — a specific user, guild, or team, or a friendlier flash/redirect — live as a controller `before_action` (e.g. `PublicApplicationsController#enforce_submission_cap`, the per-user hourly apply cap). Don't put the same limit in both layers; the two defend different things (infrastructure abuse vs. one authenticated actor doing something too often). Rack::Attack uses an in-memory `MemoryStore` (fine while Puma is single-process — see `config/puma.rb`); controller caps use `Rails.cache` (Solid Cache, durable). Rack::Attack is disabled in the test env (the suite blows past the limits from `127.0.0.1`); a test that needs it flips `Rack::Attack.enabled` on and calls `reset!`.
